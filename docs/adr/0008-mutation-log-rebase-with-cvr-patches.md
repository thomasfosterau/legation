# ADR-0008: Mutation-log writes with server rebase; CVR state patches downstream

Date: 2026-06-12
Status: Accepted — supersedes ADR-0005 (per-key versions with push-time conflict detection); narrows ADR-0004 to the HTTP cache module

## Context

ADR-0005 synced state diffs: clients pushed new values per key with a `baseVersion`, the server detected conflicts by version mismatch, and clients resolved them with merge strategies (`preferLocal`, `preferRemote`, `lastWriteWins`, custom). State diffs cannot preserve intent under concurrency — "increment" replayed as "set to 5" clobbers — so every conflict needs an explicit strategy, and offline queues of state diffs compound the problem. The battle-tested alternative (Replicache, Zero, and the shape of Effect's own EventLog) is to sync _intents_: named mutator functions executed optimistically on the client and authoritatively on the server, with the client rebasing pending intents on top of incoming authoritative state.

Downstream, two models were considered: replicating event logs per scope (simple, offline-natural, but whole-scope sync only) and server-computed state patches against a per-client view record (partial sync, read authorization, large datasets, more server machinery).

## Decision

**Writes**: a mutation is a named, schema-validated intent (mutator name + args) with a per-client sequential mutation id. Mutations append to a durable client journal, apply optimistically to local collections, and are pushed to the backend, which executes its own (possibly different) implementation of the mutator transactionally — the mutation-id bump atomic with the effects, giving exactly-once in-order application.

**Downstream**: the server tracks a client view record (CVR) — exactly which row versions each client holds per subscription — and computes minimal row put/delete patches. `Pull(cookie) → patch` is the canonical path; sync must be correct over pull alone (periodic HTTP-only sync works). Live delivery of the same patches over a streaming connection, and pokes, are latency optimizations.

**Conflicts**: there are no merge strategies. On every incoming patch the client rewinds to authoritative state, applies the patch, replays pending mutations on top (which may compute different effects against newer state), and reveals the result atomically. A pending mutation's optimistic effects are dropped only when that mutation's authoritative outcome is observed — never merely when the request resolves.

ADR-0004's mark-stale invalidation semantics survive only in the HTTP cache module; collections have no stale marking — they have patches and the overlay.

## Consequences

- Intent-preserving conflict resolution with no strategy vocabulary to teach; the cost is that every write must be expressible as a named mutator (no ad-hoc `set(key, value)` sync).
- True partial sync, per-subscription read authorization, and large backing datasets become possible; the price is real server machinery (CVR storage, diffing) — contained by ADR-0009's contract split.
- Offline-first falls out: the journal is durable, pulls are resumable from a cookie, and rebase handles whatever happened while offline.
- An unrecognized or lost cookie degrades safely to a reset patch (clear + full puts), so CVR storage may be ephemeral.

## Addendum: compacting the unpushed tail (#117, #249)

"Pushed journal entries never change" is the boundary; the unpushed tail is local and may be compacted (paced mutations drop superseded entries). The backend's ledger still requires a client's ids to arrive without gaps, so the client **renumbers** the surviving unpushed entries contiguously, in order, and rewinds its id counter; the backend is not asked to accept gaps. An entry a push has been attempted for, successful or not, is frozen: a lost response does not prove the backend did not apply it, and renumbering an applied entry would get a later write skipped as a duplicate. Clients therefore record, durably and before a request leaves, the highest id each push may have sent (`ClientStore.markSent`), and treat a journal found at boot, or hydrated from a snapshot, as already sent.

## Addendum: the push acknowledgement and the overlay (#286)

The Decision says a pending mutation's optimistic effects are dropped "only when that mutation's authoritative outcome is observed — never merely when the request resolves". Before #286 the engine dropped them at the push acknowledgement, so an observer saw the pre-mutation value until the next pull. The engine now keeps an acknowledged mutation's effects overlaid until a pull reports it. That is the rule for the push-acknowledged path. The carve-outs are listed under Bounds and Durability below and tracked as #337 and #336.

- **Push ack.** The backend applied the entries the response covers. They are trimmed from the journal, so they are never sent again, and parked in an in-memory, oldest-first **acknowledged tail** (CONTEXT.md, "Unpulled tail"). The overlay replays that tail ahead of the pending journal, so a push reveals nothing. A permanently rejected entry was not applied and leaves the overlay at its push.
- **Pull.** The pull's patch carries the effects of everything its `lastMutationIds` covers, so the pull releases the tail entries it covers. The write of the confirmed rows, the release and the cache invalidation run as one critical section under the overlay lock, and the rebase is revealed in one change. A read in between would otherwise replay the tail over rows that already hold its effects.
- **Server ordering.** The pull's watermark and rows are one snapshot. The server reads `lastMutationIds`, evaluates and assembles the patch, then reads `lastMutationIds` again. On a backend that meets Backend guarantee 1, a client's id is bumped in the same commit as its effects, so an unchanged watermark means no push committed in between: the rows hold every push the watermark covers, and no push they hold is uncovered. A backend that exposes effects before the bump can still hand a pull an uncovered effect, which the client double-applies until the next pull. MemoryBackend (#341) and SqlBackend on D1 (#342) do this today. A push that lands mid-read moves the watermark, and the view is read again, up to three passes. Read before the rows only, the watermark could leave a push out while its effects were in the patch, and the client would replay it over them (a double application). Read after the rows only, it could report a push whose effects the patch lacks (a revert under this rule). The server records the CVR once, for the view it returns. Each extra pass costs a full view evaluation; a server that disturbs all three passes logs a warning.
- **Bounds and resets.** The tail holds at most 1024 entries. Past that, the oldest are released with a `logWarning`, so a view can revert without a pull (#337). Two more cases revert transiently, each until the next pull: a server that disturbs all three passes returns the watermark read after its patch, and a restart or a BackgroundSync flush (Durability, #336). An identity reset clears the tail with the rows it was overlaid on. An upgrade keeps it.
- **Client lock.** A pull writes its confirmed rows and releases the tail inside the overlay lock, so reads and mutations wait on the store's patch write. The section is not failure-atomic: a store error between the two leaves the view double-counting until the next successful pull.
- **Pull trigger.** A client with no poke and no `pullInterval` keeps its acknowledged effects overlaid until its next pull, however long that takes. The rule is kept by holding the effects; scheduling is unchanged by this addendum.
- **Durability.** The tail is held in `ClientStore` (#336), in the memory, key-value and IndexedDB stores, so a restart, a snapshot and the BackgroundSync push-only flush (`packages/browser/src/BackgroundSync.ts`, which pushes without pulling) keep its effects overlaid until a pull reports them. It is kept out of the pending journal, so it is never pushed again. A push parks an entry in the tail before it trims the journal, and a pull records its watermark before it writes its rows, so a crash in either window is settled on the next open: each entry is then in the tail alone, or the release is finished. The one revert left is a crash after a pull records its watermark and before its first row write. The covered entries then show the confirmed rows until the next pull, as a restart did before this change. An identity reset clears the tail, and a snapshot carries it as an optional field that an older snapshot leaves empty.
- **MutationState.** `acknowledged` (and `mutateWithAck`'s `applied`) still fires at the push ack, meaning the backend applied the mutation. The overlay's visibility now follows the pull instead.
