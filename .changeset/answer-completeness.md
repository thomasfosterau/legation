Add `Client.answer(read)` and `Client.observeAnswers(read)`, which give a read's rows with their completeness beside them (#653): a `Client.Answer<R, G>`, `{ rows, completeness }`, where `completeness` (`Client.Completeness`) is `"complete"` when a pulled subscription covered the read or the server answered it, and `"partial"` when an uncovered read was answered from the replica (offline, or over a transport without `read`), which may hold fewer rows than the server. Both are checked and typed as `query` and `observe` are (`AnswerOf<G>`, `ObserveAnswersOf<G>`), so `answer.rows` holds the read's typed rows. An `observeAnswers` stream is partial until the read's windows are pulled, then emits the rows again as complete. Rows are called complete only when they were read after the pull marks that cover them: on each emission and each pull the Client reads the read's rows again rather than relabelling rows that may predate the pull. `query` and `observe` are unchanged. `ClientView` gains an optional `pulledChanges` stream, which the Client uses to judge a live read again after a pull, and an optional `queryRelated`, which reads a held relational read's current rows (a `Mirror` answers it from its host's rows). An engine-backed view's relational read now records pull marks under its relational key, as a pin with `include` does.
