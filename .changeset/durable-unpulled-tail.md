Make the acknowledged-but-unpulled tail durable in `ClientStore` (#336). A push acknowledgement parks the applied mutations in the store, out of the pending journal, so they are never pushed again. Their effects stay overlaid until a pull reports them, and now also across a restart, a hydration snapshot and the BackgroundSync push-only flush. A restart between a push acknowledgement and the next pull no longer shows the confirmed rows without the mutation.

- **Pull release.** A pull records its whole release in the store before it writes its rows: the watermark, the cookie and the patch. An open that finds the record finishes the pull (it re-applies the patch, which is idempotent, writes the cookie, trims the journal and releases the tail), so a crash at any point shows the pull's effects, never the rows without them. A release that fails part-way is finished in the same process, including one whose record write reports failure after it landed. If that roll-forward also fails, the store seals itself until it is reopened.
- **Row writes during a release.** While a release is outstanding, `putRow`, `delRow` and `clearRows` finish it first, under the same store lock, and fail if they cannot. The engine's `seed`, its `clearRows` and its identity reset hold the overlay lock for their row writes. A hydration snapshot finishes an outstanding release before it writes.
- **Identity reset.** The tail is cleared with the rows it was overlaid on, in the store's open-time reset and in the engine's runtime reset. The store drops any release record with it.
- **Trim.** A push whose journal trim fails leaves the parked entries out of the journal in the same process, as an open does, so they are not pushed again or replayed twice.
- **Hydration.** `Hydration.SnapshotSchema` gains an optional `unpulled` field. `dehydrate` writes it when the tail is not empty; `hydrate` parks it. A snapshot without the field loads with an empty tail.
- **IndexedDB.** The tail uses the existing key-value layout, so there is no new object store or index and the database version does not change.

Action required: a custom `ClientStore` must implement six new members: `unpulled`, `parkUnpulled`, `beginRelease`, `releaseUnpulled`, `finishRelease` and `clearUnpulled`. `ClientStore.makeMemory`, `ClientStore.makeKeyValue` and `IndexedDbClientStore` already do. `beginRelease` refuses while a release is outstanding. `finishRelease` rolls an outstanding release forward from the record `beginRelease` stored, and a store that cannot do so must fail its later calls, as a sealed store does. `beginRelease` may be a no-op only for a store that cannot survive a restart. In a store that does survive a restart, a no-op `beginRelease` double-counts after a crash mid-release, rather than reverting. Implementing the tail members as no-ops in such a store silently reverts the overlay after a restart: the tail is lost and the confirmed rows lack the acknowledged mutations until the next pull.
