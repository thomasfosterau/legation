# Domain Context

The legation monorepo implements a data synchronization engine built on Effect. This glossary defines the project's vocabulary; use these terms (not synonyms) in code, issues, and docs.

Coming from TanStack Query, SwiftData, SWR, or Apollo? [`docs/coming-from-tanstack-query.md`](docs/coming-from-tanstack-query.md) translates those libraries' vocabulary into the terms below. This file is the internal law; that guide is the outward-facing translation. For how legation relates to Convex, Zero, TanStack DB, Replicache, ElectricSQL, and the native-platform stacks (SwiftData, Room), see [`docs/comparisons/`](docs/comparisons/README.md).

The engine follows the mutation-log/rebase sync model (ADR-0008): named write intents flow up, server-computed state patches flow down, and the client rebases pending intents on top of authoritative state.

> **ADR-0022, landed:** this glossary describes the resource-graph public API — six concepts: **Node, Collection, Query, Mutation, Client, Server** — and `@legation/effect`'s root index now exports exactly that surface (plus the Backend contract, Authorization vocabulary, wiring seams, and errors). The pre-0022 machinery (`Subset`, `ClientEngine`, `ClientView`, `Mirror`, `SyncServer`, `InvalidationBus`, …) lives behind `@legation/effect/internal` for adapter authors; `Mutator` remains as a deprecated alias of `Mutation`.

## Glossary

### Data model

| Term            | Meaning                                                                                                                                                                                                                                                                                                                                                                  |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Node**        | A typed resource: scalar attributes plus edges to other nodes. Defined with Effect Schema; ids are branded per node type (ADR-0022).                                                                                                                                                                                                                                     |
| **Edge**        | A node's relationship to other nodes — `one`, `many`, or `paginated`. A collection-valued edge IS the dependent collection `target where fk = parent id`: a view over one foreign key (declared once on the child, named in both directions), never storage. The same key powers the join, the sync window, the auth scope (ADR-0015), and the fan-out topic (ADR-0023). |
| **Collection**  | The named set of one Node type, derived from the Node definition — the unit the client materializes locally and queries. The replica is normalized: a node lives once in its collection; windows hold memberships, never copies.                                                                                                                                         |
| **Row**         | One value in a collection, identified by (collection, row id), carrying a row version assigned by the backend.                                                                                                                                                                                                                                                           |
| **Row version** | An opaque per-row token the backend changes on every authoritative write. The basis for computing what a client is missing.                                                                                                                                                                                                                                              |
| **Schema**      | The Effect Schema describing a collection's row type; the single source of truth for validation, serialization (wire + persistence), and inference.                                                                                                                                                                                                                      |

### Writes

| Term                    | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Mutation**            | A named, schema-validated write intent (name + args) defined once and executed twice: optimistically on the Client, authoritatively on the backend (ADR-0008 unchanged). One _invocation_ carries the args and a per-client sequence number.                                                                                                                                                                                      |
| **Mutation id**         | A per-client sequential number on each mutation, giving the backend exactly-once, in-order application and giving the client precise acknowledgement.                                                                                                                                                                                                                                                                             |
| **Journal**             | The client's durable, causally-ordered log of pending mutations awaiting backend acknowledgement. Survives reloads and crashes.                                                                                                                                                                                                                                                                                                   |
| **Pending mutation**    | A journal entry not yet acknowledged by the backend. Its local effects live in the optimistic overlay and are replayed on every rebase.                                                                                                                                                                                                                                                                                           |
| **Optimistic overlay**  | The local effects of pending mutations, rendered above confirmed rows. Dropped per-mutation exactly when that mutation's authoritative effect is observed — never merely when the request resolves.                                                                                                                                                                                                                               |
| **Rebase**              | On incoming authoritative state: discard optimistic effects, apply the patch, replay pending mutations on top, and reveal the result atomically. Conflict resolution _is_ replay: mutators may compute different effects against newer state.                                                                                                                                                                                     |
| **Transient failure**   | A backend failure that may succeed on retry (deadlock, timeout, lost connection). The push batch is aborted and the client retries; no mutation id is bumped. Signalled by a `BackendError` from a mutator handler.                                                                                                                                                                                                               |
| **Permanent rejection** | A backend refusal a retry can never overcome (failed validation, revoked permission, violated business rule). The backend bumps the `mutation id` _without_ applying effects, atomically — so the mutation is acknowledged and skipped rather than poisoning the queue, mutations behind it still apply, and the client drops the optimistic effect on the next rebase. Signalled by a `MutationRejected` from a mutator handler. |

### Sync protocol

| Term                         | Meaning                                                                                                                                                                              |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Subscription**             | A client-registered collection subset — (collection, predicate, order, limit/cursor) — that the backend keeps synced to the client.                                                  |
| **Predicate**                | A serializable expression tree over row fields, used in subscriptions. Client predicates can only narrow what auth filters allow.                                                    |
| **Client view record (CVR)** | The server-side record of exactly which row versions a client holds, per subscription. The basis for computing minimal patches.                                                      |
| **Cookie**                   | The opaque token a client presents on pull, identifying the CVR snapshot it has.                                                                                                     |
| **Patch**                    | An ordered sequence of row put/delete operations moving a client's view from one cookie to the next.                                                                                 |
| **Push**                     | The client delivering pending mutations to the backend.                                                                                                                              |
| **Pull**                     | The client requesting a patch: cookie + subscriptions in, patch + new cookie + mutation acknowledgements out. The canonical correctness path — sync must be correct over pull alone. |
| **Poke**                     | A contentless "pull soon" hint. Realtime delivery is a latency optimization, never a correctness dependency.                                                                         |
| **Sync transport**           | The carrier moving protocol messages between client and server. Messages are schema-defined; carriers are pluggable (the RPC implementation is the default).                         |

### Reads

| Term            | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Query**       | THE read concept (ADR-0022): a declarative description — collection, `where`, `include` (edges, with per-edge cursors), `order`, cursor pagination — that compiles internally to a plan of sync windows (root window + one per traversed edge). Named/parameterized queries are the same concept with a name and args schema.                                                                                                                                                                                                                                                                                                                         |
| **Client**      | The one-per-thread object that runs many queries and mutations. Where a query is answered — local replica, an engine hosted elsewhere (service worker, Electron main, a daemon), or server fallthrough for uncovered reads — is configuration, never a concept the UI sees. Carries the sync-protocol identity (clientId, client group, CVR cookie) as internal state.                                                                                                                                                                                                                                                                                |
| **Live query**  | A query observed over the local replica: results re-emit when rows it depends on change (never a refetch). Row-level `enter`/`update`/`exit` deltas over a subset's window — for keyed-list bindings and side-effect subscriptions — are `observeChanges`, on the engine and `ClientView`/`Mirror` alike; see [`docs/observing-row-changes.md`](docs/observing-row-changes.md). Live queries _compose_: client-local combinators (`Derive` — filter/map/join/groupBy/distinct/ordered window) derive one live query from others, incrementally maintained over only the already-synced rows — a shaping tier that never widens what syncs (ADR-0027). |
| **Mirror**      | _(internal)_ A client context's in-memory copy of its subscribed rows, hydrated and kept current by engine-host broadcasts — the machinery behind `Client.connect`. Holds no durable state; can only answer for registered keys, so observing auto-registers.                                                                                                                                                                                                                                                                                                                                                                                         |
| **Engine host** | _(internal)_ Where the sync engine runs when a Client connects to it rather than owning it. In browsers the recommended host is a service worker (the per-origin singleton); the engine itself is host-agnostic.                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **Client view** | _(internal, superseded by **Client**)_ The narrow surface bindings consume, satisfied by an owned engine or a connected mirror alike (ADR-0021's one-surface principle, now carried by the Client).                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

### Server

| Term                 | Meaning                                                                                                                                                                                                                                                                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Backend**          | The app-owned storage and mutator-execution environment fulfilling the server contract: run mutators transactionally (mutation-id bump atomic with effects) and evaluate subscriptions to (row id, row version) sets.                                                                                                                       |
| **Auth filter**      | A mandatory server-side predicate per collection, AND-ed into every subscription before evaluation. Deny by default.                                                                                                                                                                                                                        |
| **Sync middleware**  | A server-side interception point over subscription and push handling, for cross-cutting concerns (tenancy, cost control, telemetry).                                                                                                                                                                                                        |
| **Session**          | One connected client as seen by the server: its identity, subscriptions, and transport connection.                                                                                                                                                                                                                                          |
| **Server**           | The one server-side object (ADR-0022): handler (push/pull/CVR diffing) + `broadcast`, over the backend and auth seams; CVR storage, fan-out brokers, and hint sources are options. Logical — its parts deploy separately (a room per user, fan-out shards).                                                                                 |
| **Broadcast**        | The single server-side verb for "these resources changed": implicit on mutation writes (topics derived from written values), explicit for out-of-band writers. Publishes hints; poke-then-pull semantics underneath (ADR-0019).                                                                                                             |
| **Topic**            | A fan-out routing key derived from the Node/Edge graph (ADR-0023): coarse `collection`, fine `collection/field=value` for fields in the derivable set. Rooms lease registrations per topic; writes publish to their topics' shards.                                                                                                         |
| **Derivable set**    | The fields of a node eligible for fine topics: its edges' foreign keys plus declared `hintKeys`. Declared on the Node, so registration and write-derivation cannot disagree — under-poking is impossible by construction.                                                                                                                   |
| **Invalidation bus** | _(internal)_ The pluggable topic-keyed channel carrying committed-write hints to sessions, possibly across instances — `broadcast`'s transport (in-process, Redis Streams, Durable Object shards).                                                                                                                                          |
| **Hint source**      | A producer of change hints for out-of-band writers — cron, admin tools, another service, `psql` — that publishes to the invalidation bus so writes bypassing the mutators still poke subscribers. The polling source (`@legation/sql`) is the shipped SQL implementation; see [`docs/change-data-capture.md`](docs/change-data-capture.md). |
| **Room**             | The per-user deployment unit of the Server (formerly "sync room"): that user's sessions (WebSockets), CVRs, and topic leases — an in-process object or a per-user Durable Object alike (ADR-0022's reference topology).                                                                                                                     |
| **Fan-out**          | Recomputing and delivering patches to every session whose subscriptions a committed write may affect.                                                                                                                                                                                                                                       |

### HTTP cache (service-worker module)

| Term                       | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **HTTP cache**             | The separate service-worker module caching fetch-event Request/Response pairs via the browser Cache API.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Freshness**              | A cached response is _fresh_ (serve it), _stale_ (serve-then-revalidate), or _expired_ (must reload).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Stale-while-revalidate** | Serving a stale cached response immediately while refreshing it in the background.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| **Tag**                    | A label attached to cached responses for group invalidation. The convention is `collection:{name}`: a response tagged `collection:todos` is evicted whenever the `todos` collection changes, so a synced pull drives HTTP-cache invalidation (`HttpCacheInvalidation` in `@legation/browser`). This is a **collection-level granularity ceiling** — every response tagged for a changed collection is evicted, even one a finer diff would have spared. A per-row `collection:{name}:{id}` tag could follow the same convention once patch-op row ids are plumbed through to the change feed; not implemented today. |

## Delivery guarantees (hub backpressure)

Every in-process message hub is bounded, so a slow or stalled consumer cannot
make a producer grow a queue without limit. Because **pull is the correctness
path** (ADR-0008), each hub can shed load under pressure without threatening
convergence — a dropped hint or poke only delays the next pull, and a dropped
`Patch` is only ever dropped behind a forced `Rebuild` that subsumes it.

| Hub                                      | Bound + policy                          | What may be shed, and why it is safe                                                                                                                                                                                                           |
| ---------------------------------------- | --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Poke hub** (`Transport.makePokeHub`)   | `sliding(1)` per client group, replay 1 | A poke is a contentless "pull soon" hint, so a storm collapses to one queued poke per group: an outstanding poke absorbs any number of fresh ones. A missed poke only delays the next pull. Replay 1 covers the reconnect race.                |
| **Invalidation bus** (`InvalidationBus`) | `dropping` at a configurable capacity   | A dropped hint only delays the next pull, which recovers the missed change (ADR-0009). Drops are counted in `legation_hints_dropped_total`.                                                                                                    |
| **Engine change hub** (`ClientEngine`)   | `dropping` at a configurable capacity   | Each view-change carries a monotonic seq; a consumer that sees a seq gap (a drop) collapses it into a full `Rebuild`, which subsumes the dropped `Patch`es. Lossless. Collapses are counted in `legation_change_collapses_total`.              |
| **Mirror change hub** (`Mirror`)         | `dropping` at a configurable capacity   | The hub carries subset keys; the newest rows live in a `Ref`. A seq gap makes the observer re-read its subset from the `Ref` — a full refresh, lossless because the `Ref` holds the latest rows. Counted in `legation_mirror_refreshes_total`. |

A `Patch` view-change is never silently dropped: the change hub only ever sheds
a `Patch` behind a seq gap, and the gap forces a `Rebuild` before the view is
next read, so no confirmed delta is ever lost.

## Packages and their bounded contexts

Package boundaries follow dependency footprint (ADR-0006): everything needing only `effect` is in core. Runtime globals count as dependencies.

| Package                | Context                                                                                                                                                                                                                                                                                                                                                                       |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@legation/effect`     | The engine, public surface per ADR-0022: Node/Edge/Collection (the resource graph), Query, Mutation, Client, Server, Backend (+ Errors). Everything else — journal/overlay/rebase, live-query reactivity, protocol messages + transport seam, CVR bookkeeping, the topic fan-out broker, the mirror seam, HTTP cache, spec export — is internal machinery behind those eight. |
| `@legation/browser`    | Browser-runtime adapters: service-worker host composition, IndexedDB client store, the mirror seam's BroadcastChannel binding.                                                                                                                                                                                                                                                |
| `@legation/node`       | Node-runtime adapters for serving the protocol.                                                                                                                                                                                                                                                                                                                               |
| `@legation/jsonapi`    | The first-class effect-jsonapi bridge (ADR-0022): a `Resource` graph converts to/from Nodes, plus the JSON:API v1.1 document loaders. One domain definition drives the wire API and the replica.                                                                                                                                                                              |
| `@legation/sql`        | Driver-agnostic SQL reference backend: `Subset`→`WHERE` translation (SQLite/Postgres) over a minimal executor seam (subset evaluation, row fetch, transactional idempotent mutation-id ledger).                                                                                                                                                                               |
| `@legation/cloudflare` | Cloudflare-runtime adapters: Durable-Object-hosted rooms and the edge transport.                                                                                                                                                                                                                                                                                              |
| `@legation/svelte`     | Svelte bindings: `setClientRuntime` + the `Runes` hooks (`useQuery` / `useConnection` / `useAggregate` / `useMutation`) over the reactivity atoms; the `Readable` store tier on the package root remains for Svelte 4.                                                                                                                                                        |
| `@legation/sveltekit`  | SvelteKit integration: the client-group cookie, SSR loads that seed the hooks with what the page already fetched, and tab boot.                                                                                                                                                                                                                                               |
| `@legation/devtools`   | Headless devtools core over an owned engine + store (journal, subsets, forced push/pull, simulated offline), with a Svelte panel on `/svelte`.                                                                                                                                                                                                                                |

## Avoided terms

- ~~"Outbox"~~ → say **journal**
- ~~"Sync hub" / "sync room"~~ → say **Room** (the per-user unit) or **Server** (the whole) or **backend** (the storage/execution contract)
- ~~"Server store"~~ → say **backend**
- ~~"Conflict strategy"~~ → conflicts resolve by **rebase** (mutator replay); there is no per-key merge-strategy vocabulary
- ~~"Query cache" / "refetch"~~ → live queries don't refetch; they re-run over local collections when patches or the overlay change
- ~~"Garbage collection / gcTime"~~ → say **time to live / expiry**
- ~~"Document"~~ (except in the JSON:API package where it's the spec's term)
- ~~"Mutator"~~ → say **Mutation** (definition and invocation share the noun; code may lag until ADR-0022's program lands)
- ~~"Relationship"~~ → say **edge** (except in the JSON:API package where it's the spec's term)
- ~~"Subset" / "Predicate"~~ as public vocabulary → a **Query** compiles to a plan of **windows**; subsets/predicates are the plan's internal representation
- ~~"TabMirror"~~ → **Mirror**, and only as internal vocabulary (the public concept is the **Client**)

For the reverse mapping — where a TanStack Query / SwiftData / SWR / Apollo term lands in this vocabulary — see [`docs/coming-from-tanstack-query.md`](docs/coming-from-tanstack-query.md).
